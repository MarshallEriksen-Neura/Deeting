## Who this page is for

Read this page first if you are:

- contributing to the main Deeting repository
- trying to understand the split between web, desktop, and backend
- planning to build a Deeting plugin
- looking for the right starting point instead of reading the whole monorepo at once

## Stack overview

- Next.js App Router
- React 19
- next-intl for internationalization
- Tauri for desktop runtime
- Local and cloud capability modules

## Read the repo by lane first

It is usually easiest to understand Deeting by lane:

- `deeting/`: web and desktop frontend
- `deeting/src-tauri/`: desktop local runtime
- `backend/`: cloud services and APIs
- `docs/`: plans, designs, and historical notes
- `packages/`: plugin development packages and scaffolding

This matters because the same product term can map to different sources of truth in different lanes.

## Engineering advice

- Keep desktop-local, backend-cloud, plugin market, and admin surfaces separate
- When a bug looks visual, verify transport and storage contracts first
- Preserve a clear source of truth when introducing new behavior

## If you want to build plugins, start with `create-deeting-plugin`

If your goal is plugin development, the most useful entry point is the scaffold:

```bash
bunx create-deeting-plugin
```

Relevant repo locations:

- `packages/create-deeting-plugin`
- `packages/README.md`

This scaffold gives you a standard plugin structure so you do not need to start from an empty directory.

## What the scaffold gives you

A standard plugin generated by `create-deeting-plugin` includes:

- `deeting.json` for metadata, permissions, capabilities, and entrypoints
- `main.py` for backend logic
- `llm-tool.yaml` for the callable host tool contract
- `SKILL.md` for behavioral guidance and constraints
- `ui/index.html` for optional frontend rendering

## The most important rule in plugin development

Keep these files in sync:

1. `llm-tool.yaml`
2. `main.py`
3. `SKILL.md`

If you rename a tool or change its arguments or behavior, update them in that order:

1. callable schema first
2. backend implementation second
3. behavior guidance last

## How to approach a new plugin

For a first plugin, this is the safest path:

1. Run `bunx create-deeting-plugin`
2. Decide what callable tool you want to expose
3. Define it in `llm-tool.yaml`
4. Implement it in `main.py`
5. Add `ui/index.html` only if the plugin needs custom rendering
6. Document usage and constraints in `SKILL.md`

## When you need to go deeper into the main repo

You usually only need deeper platform context when:

- you are debugging install, publish, review, or market flows
- you need to understand how desktop loads or invokes plugins
- you are debugging permission, registration, or runtime issues
- you are changing platform behavior rather than shipping a standalone plugin
