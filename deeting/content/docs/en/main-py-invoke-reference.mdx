## What this file is

`main.py` is the backend execution entrypoint for a plugin.

In the default template, the actual runtime logic starts here.  
The key contract is the `invoke` function:

```python
async def invoke(tool_name, args, deeting):
    ...
```

This is the backend path the host will actually call.

## Minimal example

```python
from typing import Any

async def invoke(tool_name: str, args: dict[str, Any], deeting: Any) -> Any:
    deeting.log(f"Executing tool: {tool_name} with args: {args}")

    if tool_name == "hello_deeting":
        name = args.get("name", "Stranger")
        return {"message": f"Hello {name}!"}

    raise ValueError(f"Unknown tool: {tool_name}")
```

## The three core inputs

### `tool_name`

The tool selected by the host.

It should stay aligned with:

- the `name` in `llm-tool.yaml`
- the tool references described in `SKILL.md`

### `args`

The arguments passed into the tool call.

These should follow the structure defined in `llm-tool.yaml`.

### `deeting`

The host-injected SDK object.

In current plugin guidance, it typically exposes helpers such as:

- `deeting.log(...)`
- `deeting.render(...)`
- `deeting.call_tool(...)`
- `deeting.section(...)`

## What `main.py` should do

It is the right place for:

- dispatching by `tool_name`
- reading and validating arguments
- executing core logic
- returning results
- calling `deeting.render(...)` when richer UI output is needed

## What `main.py` should not own

It should not be the source of truth for:

- callable schema
- package metadata and permissions
- behavior guidance

Those belong in:

- `llm-tool.yaml`
- `deeting.json`
- `SKILL.md`

## When to use `deeting.render(...)`

If the plugin only needs to return a structured result, a normal `return` is often enough.

If it should also display a richer frontend block, use:

```python
deeting.render(
    view_type="bento.grid",
    title="Plugin Response",
    payload={...}
)
```

## Common mistakes

1. `tool_name` no longer matches `llm-tool.yaml`
2. assuming `args` are always complete
3. changing the returned shape too often
4. forgetting that the frontend may depend on the backend response structure

## Safe implementation advice

- keep one tool focused on one job
- read arguments directly and clearly
- keep output shapes stable
- raise useful errors when something is missing or unknown

## If one plugin exposes multiple tools

In that case, `main.py` usually becomes a small dispatcher:

```python
if tool_name == "tool_a":
    ...
elif tool_name == "tool_b":
    ...
else:
    raise ValueError(...)
```

If the file grows too much, split internal helper functions, but do not over-abstract too early.
