## Who this is for

- Developers integrating Deeting into external systems
- Teams evaluating MCP, plugins, or capability extensions
- Engineers connecting internal tools to existing workflows

## First, identify what you are integrating

In Deeting, “integration” can mean several different things:

- `Public API`
  Best when you want to connect external systems to platform capabilities.

- `MCP or tool capability integration`
  Best when you want Deeting to call external tools or services during execution.

- `Plugin development`
  Usually the most approachable path for external developers extending Deeting.

- `Desktop-local capability paths`
  Best for machine-local scenarios, but different from public cloud integration.

## Three questions worth answering early

1. Are you integrating with a cloud capability or a desktop-local capability
2. Do you need executable capability or only documentation-level guidance
3. Is your current blocker about permissions, configuration, runtime, or contract definition

## Recommended approach

1. Identify the lane
2. Identify the source of truth
3. Understand permissions, runtime boundaries, and dependencies
4. Validate one minimal happy path before expanding scope

## If you want to build plugins, start with `create-deeting-plugin`

For most external developers, the best starting point is:

```bash
bunx create-deeting-plugin
```

The scaffold gives you a standard plugin structure including:

- `deeting.json`
- `main.py`
- `llm-tool.yaml`
- `SKILL.md`
- `ui/index.html`

That lets you focus on defining the callable contract and implementing behavior rather than inventing your own packaging model.

## The most important rule for plugin integration

Keep these aligned:

1. `llm-tool.yaml`
2. `main.py`
3. `SKILL.md`

The callable schema should lead, the backend should implement it, and the skill guidance should describe how and when it should be used.

## If you are integrating MCP or tool capabilities

This path is a better fit once you have already defined:

- the tool boundary
- the input and output contract
- the risk and permission model
- the real source of truth for the capability

## If integration looks correct but still fails

Check these in order:

1. wrong lane selection
2. permission or approval mismatch
3. configuration present but runtime dependency missing
4. UI symptom hiding a transport, invoke, or host registration problem
