## 适合谁阅读

- 想从外部系统接入 Deeting 的开发者
- 想理解 MCP、插件或能力扩展边界的团队
- 想把内部工具接入现有工作流的工程师

## 先不要急着接，先分清你在接什么

在 Deeting 里，“集成”并不是单一含义。开始之前，建议先分清楚自己属于哪一种场景：

- `公开 API`
  适合从外部系统调用平台能力，或者把 Deeting 作为外部服务接入现有系统。

- `MCP / 工具能力接入`
  适合把外部能力、工具或服务挂到 Deeting 可调用的执行链路中。

- `插件开发`
  适合希望用标准插件形态扩展 Deeting 的开发者。通常这是外部开发者最容易开始的一条路。

- `桌面本地能力`
  适合更贴近本地运行时的场景，但它和公开 API、云端能力并不是一回事。

## 开始前最值得先问自己的三个问题

1. 你接入的是 `云端能力`，还是 `桌面本地能力`
2. 你需要的是 `可执行能力`，还是 `文档/说明层面的指导`
3. 你当前的阻塞来自 `权限`、`配置`、`运行时`，还是 `契约定义`

这三个问题如果不先想清楚，后面很容易把配置问题误判成产品问题，或者把桌面问题误判成后端问题。

## 推荐的接入顺序

1. 先确定 lane
2. 再确认 source of truth
3. 明确权限、运行边界和依赖前提
4. 先打通一个最小闭环
5. 最后再扩展功能面

## 如果你想做插件，优先使用 `create-deeting-plugin`

对于外部开发者来说，最推荐的起点是插件脚手架：

```bash
bunx create-deeting-plugin
```

这个脚手架会生成一套标准插件结构，包括：

- `deeting.json`
- `main.py`
- `llm-tool.yaml`
- `SKILL.md`
- `ui/index.html`

这意味着你不需要从零设计文件结构，而是可以直接开始定义工具契约、实现逻辑和可选 UI。

## 插件集成时最重要的原则

如果你走插件路线，请优先记住这几个规则：

1. `llm-tool.yaml` 是可执行工具契约
2. `main.py` 必须实现和契约一致的行为
3. `SKILL.md` 是行为说明，不替代可执行工具定义
4. `deeting.json` 用于元数据、权限和入口声明

最常见的错误不是“代码不会写”，而是这些文件之间没有同步更新。

## 如果你想接 MCP 或工具能力

这类集成更适合已经明确了工具边界、参数输入和调用风险的团队。

建议先明确：

- 工具是否真的需要暴露给模型调用
- 权限和风险控制应放在哪一层
- 是做成独立服务、MCP server，还是插件能力
- 谁是这个能力的 source of truth

## 如果你在集成过程中遇到问题

建议按下面顺序排查：

1. 是接入 lane 选错了，还是能力本身没打通
2. 是权限或审批问题，还是接口契约不一致
3. 是配置看起来对，但运行时依赖缺失
4. 是前端显示问题，还是 transport / invoke / host registration 问题
