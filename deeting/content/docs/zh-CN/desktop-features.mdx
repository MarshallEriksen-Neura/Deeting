## 为什么会有桌面端

Deeting 桌面端并不是网页端的简单壳层。

它存在的意义，是把一部分更贴近本地运行时的能力带到产品里，例如系统级交互、本地能力执行、窗口与托盘行为，以及某些本地知识或扩展路径。

如果你只需要基础浏览与使用，网页端已经足够；  
如果你希望获得更完整的本地工作体验，桌面端会更适合。

## 当前已经融入的主要能力

- `本地聊天与运行时编排`
  桌面端可以承接一部分更靠近本地执行环境的聊天与能力调用流程。

- `系统托盘与窗口行为`
  包括关闭窗口时的守卫逻辑、隐藏到托盘、以及更符合桌面习惯的窗口交互。

- `桌面通知与系统级体验`
  某些提醒、更新、授权或运行状态更适合通过桌面端承载。

- `部分本地知识与能力路径`
  某些文件、知识或能力调用链路会更贴近本地运行环境，而不是纯网页场景。

- `桌面登录、更新与原生交互`
  包括桌面登录流程、更新流程和部分原生系统能力接入。

## 它适合什么场景

桌面端通常更适合这些场景：

- 你希望把 Deeting 作为长期打开的工作中枢
- 你需要更稳定地使用本地能力或本地运行时
- 你希望获得更完整的系统集成体验
- 你在意通知、托盘、窗口行为等桌面工作流细节

## 使用桌面端时最重要的边界

在桌面端使用 Deeting 时，最容易产生误解的地方通常有这几类：

1. `桌面本地能力` 与 `云端能力` 并不总是完全一致  
   同样的名称，在不同 lane 中可能代表不同的真实执行路径。

2. `看起来有配置` 不代表 `运行时已经可用`  
   功能可能还依赖模型、插件、MCP 服务、权限或本地环境。

3. 有些能力会触发额外的 `审批`、`授权` 或 `风险控制`  
   这不是界面问题，而是运行时安全边界的一部分。

4. 某些问题表面像 UI，实际可能是 `transport`、`invoke contract` 或 `本地状态` 问题  
   这是桌面端排查时特别常见的一类情况。

## 如果某个功能“看得见但跑不通”

建议按这个顺序排查：

1. 先确认这是桌面本地能力，还是云端能力
2. 再确认是否需要额外审批、权限或环境准备
3. 检查是否缺少模型、插件或 MCP 运行前提
4. 如果配置看起来都对，再去怀疑传输链路、调用参数或本地持久化状态
