## 先按 lane 理解仓库，而不是按文件夹数量理解

如果你第一次进入仓库，最重要的不是把每个目录都点开，而是先把系统按 lane 理解：

- `deeting/`：Web 与桌面前端
- `deeting/src-tauri/`：桌面本地运行时
- `backend/`：云端服务与 API
- `docs/`：设计、计划与历史方案沉淀
- `packages/`：插件开发相关包与脚手架

这样做的原因很简单：

- 同一个名词在不同 lane 中可能代表不同的 source of truth
- 很多问题看起来像前端问题，实际是本地运行时或后端问题
- 如果一开始 lane 选错，后面的排查会越走越偏

## 如果你要参与主仓库开发

建议先建立这几个基本判断：

- 不要把桌面本地、云端后台、插件市场和管理后台混成一个问题
- 当功能看起来是 UI 问题时，先检查 transport、invoke contract 或持久化状态
- 做新功能时尽量保留明确的 source of truth

## 如果你要开发插件，先看 `create-deeting-plugin`

对于插件开发者来说，最值得先关注的不是主仓库里所有内部实现，而是脚手架：

```bash
bunx create-deeting-plugin
```

仓库里已经有对应包与说明，入口在：

- `packages/create-deeting-plugin`
- `packages/README.md`

这个脚手架会帮你生成一套标准插件结构，让你不用从空目录开始搭骨架。

## `create-deeting-plugin` 会生成什么

一个标准插件通常会包含下面这些文件：

- `deeting.json`
  插件元数据、权限、运行入口、能力声明

- `main.py`
  后端逻辑入口。核心约定是实现：

  ```python
  async def invoke(tool_name, args, deeting):
      ...
  ```

- `llm-tool.yaml`
  可调用工具契约。它定义了宿主或 MCP 可真正执行的 tool 名称和参数结构。

- `SKILL.md`
  行为说明与使用边界。它是语义指导，不等于可执行工具定义。

- `ui/index.html`
  可选前端界面。如果插件需要渲染 UI，这里就是前端入口。

## 开发插件时最重要的同步关系

插件开发里最容易出错的地方，不是 Python 语法，而是“多份定义不同步”。

你需要特别注意这几份文件始终对齐：

1. `llm-tool.yaml`
   这是可执行工具契约

2. `main.py`
   这里要真正实现对应的 `tool_name`

3. `SKILL.md`
   这里描述行为、边界与使用说明

如果你改了工具名、参数或行为，最好按这个顺序更新：

1. 先改 `llm-tool.yaml`
2. 再改 `main.py`
3. 最后同步 `SKILL.md`

## 插件开发时，先理解每个文件负责什么

以默认模板为例：

- `deeting.json` 负责描述插件是谁、有什么权限、入口在哪里
- `main.py` 负责真正执行逻辑
- `llm-tool.yaml` 负责声明宿主可调用什么
- `SKILL.md` 负责告诉模型什么时候该用、什么时候不该用
- `ui/index.html` 负责展示插件返回的前端内容

这几个文件职责不同，不建议互相混用。

## 一个推荐的插件开发顺序

如果你是第一次写插件，建议这样做：

1. 先运行 `bunx create-deeting-plugin`
2. 先想清楚你要暴露的 tool 是什么
3. 先写 `llm-tool.yaml`
4. 再在 `main.py` 里实现对应逻辑
5. 如果需要 UI，再补 `ui/index.html`
6. 最后把使用边界和说明写进 `SKILL.md`

## 什么时候该深入主仓库

如果你只是做一个标准插件，通常不需要先完整理解主仓库所有内部实现。

更适合先看主仓库内部的情况通常是：

- 你要排查插件市场、安装、发布或审核链路
- 你要理解桌面端如何加载或调用插件
- 你要排查插件的宿主注册、权限或运行时问题
- 你要改动平台能力，而不只是新增一个插件
