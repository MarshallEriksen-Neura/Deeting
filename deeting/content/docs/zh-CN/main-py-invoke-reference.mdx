## 这是什么

`main.py` 是插件后端执行入口。

在默认模板里，插件真正的运行逻辑都从这里开始。  
它最核心的约定是实现这个函数：

```python
async def invoke(tool_name, args, deeting):
    ...
```

这就是宿主调用插件时真正会进入的后端入口。

## 一个最小示例

```python
from typing import Any

async def invoke(tool_name: str, args: dict[str, Any], deeting: Any) -> Any:
    deeting.log(f"Executing tool: {tool_name} with args: {args}")

    if tool_name == "hello_deeting":
        name = args.get("name", "Stranger")
        return {"message": f"Hello {name}!"}

    raise ValueError(f"Unknown tool: {tool_name}")
```

## `invoke` 的三个核心输入

### `tool_name`

当前被宿主选中的工具名。

它必须和下面这些地方保持一致：

- `llm-tool.yaml` 中声明的 `name`
- `SKILL.md` 中描述的工具名

如果 `tool_name` 已经改了，而 `main.py` 里还是旧名字，插件就会出现调用漂移。

### `args`

当前工具调用时传入的参数。

这些参数应该来自 `llm-tool.yaml` 中定义的参数结构，所以更稳的方式是：

1. 先定义 `llm-tool.yaml`
2. 再在 `main.py` 中按这个结构读取参数

不要先在 `main.py` 里随意发明参数，再回头补契约。

### `deeting`

宿主注入的 SDK 对象。

根据当前插件开发说明，它通常会提供一些常见能力，例如：

- `deeting.log(...)`
- `deeting.render(...)`
- `deeting.call_tool(...)`
- `deeting.section(...)`

可以把它理解成插件在运行时可用的宿主能力入口。

## `main.py` 负责什么

它最适合负责：

- 根据 `tool_name` 分发不同执行路径
- 读取和校验参数
- 调用外部能力或内部逻辑
- 返回结果
- 在需要时调用 `deeting.render(...)` 渲染 UI 数据

## `main.py` 不负责什么

为了避免职责混乱，最好记住它不负责：

- 定义工具契约
- 定义包元数据与权限
- 充当行为说明文档

这些应该分别放到：

- `llm-tool.yaml`
- `deeting.json`
- `SKILL.md`

## 一个推荐的实现思路

写 `main.py` 时，建议按这个顺序来：

1. 先判断当前 `tool_name`
2. 再读取最小必需参数
3. 执行核心逻辑
4. 需要前端展示时再调用 `deeting.render(...)`
5. 返回简洁、稳定的结果结构

## 什么时候用 `deeting.render(...)`

如果插件只是返回一个纯数据结果，直接 `return` 通常就够了。

如果插件需要在聊天流里展示一个更丰富的前端块，就可以使用：

```python
deeting.render(
    view_type="bento.grid",
    title="Plugin Response",
    payload={...}
)
```

这时你的 `ui/index.html` 或宿主侧展示逻辑就会接管渲染。

## 一个很常见的错误

很多初次开发者会犯这几类错误：

1. `tool_name` 和 `llm-tool.yaml` 不一致
2. 直接假设 `args` 一定完整存在
3. 返回结构今天一个样、明天一个样
4. 前端依赖某个字段，但后端返回结构已经改了

## 更稳的写法建议

- 一个工具只做一件明确的事
- 参数读取尽量直接、清晰
- 返回结构尽量稳定
- 如果要抛错，尽量抛出能帮助定位的错误

## 如果插件有多个工具

当插件开始支持多个工具时，`main.py` 通常会变成一个简单的分发入口。

例如：

```python
if tool_name == "tool_a":
    ...
elif tool_name == "tool_b":
    ...
else:
    raise ValueError(...)
```

如果分支越来越多，说明你可以开始考虑做内部函数拆分，但不必过早抽象。
