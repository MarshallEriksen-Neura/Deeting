## 这是什么

`llm-tool.yaml` 是插件的可执行工具契约文件。

它的作用不是描述品牌、权限或行为边界，而是明确回答：

- 这个工具叫什么
- 它是做什么的
- 它接收什么参数
- 哪些参数是必填的

你可以把它理解成“宿主真正可调用的 tool 定义”。

## 一个最小示例

```yaml
name: hello_deeting
description: "A simple tool to greet the user and show a status dashboard."
parameters:
  type: object
  properties:
    name:
      type: string
      description: "The name of the person to greet."
  required: ["name"]
```

## 最核心的字段

### `name`

工具名。

这个名字必须和 `main.py` 里真正处理的 `tool_name` 对齐。

如果这里写的是：

```yaml
name: hello_deeting
```

那么 `main.py` 里至少应该有对应分支：

```python
if tool_name == "hello_deeting":
    ...
```

### `description`

一句话解释这个工具的用途。

建议写法：

- 清晰说明这个工具做什么
- 避免写得太宽泛
- 让调用方一眼知道“什么时候该用它”

### `parameters`

参数定义。

当前模板使用的是对象结构：

- `type: object`
- `properties`
- `required`

这是最值得认真写的部分，因为它直接决定了调用契约是否清晰。

## 怎样定义参数更稳

建议遵循这几个原则：

1. 先从最小参数集开始
2. 每个参数都写清楚类型
3. 每个参数都给一句可读描述
4. 只有真正必填的参数才放进 `required`

## 一个好的参数定义应该像什么

好的参数定义通常具备这些特点：

- 参数名短而明确
- 类型和用途一致
- 描述不是废话
- 必填和可选边界清楚

坏的例子通常是：

- 一个工具带了很多暂时根本用不到的参数
- 参数名很泛，比如 `data`、`value`、`info`
- `required` 里塞满所有字段，导致调用困难

## `llm-tool.yaml` 和其他文件的关系

写这个文件时，最重要的是记住它和另外两份文件必须同步：

1. `main.py`
2. `SKILL.md`

关系可以这样理解：

- `llm-tool.yaml`
  定义“可以调用什么”

- `main.py`
  实现“调用后怎么执行”

- `SKILL.md`
  说明“什么时候该用、什么时候不该用”

## 最常见的错误

1. 改了 `name`，但 `main.py` 还在判断旧的 `tool_name`
2. 参数结构改了，但实现代码还按旧参数读取
3. `description` 太空泛，导致工具边界不清楚
4. 一开始就设计了过大的参数面

## 一个推荐的编写顺序

1. 先写工具名和一句话用途
2. 再定义最小参数集
3. 再去写 `main.py`
4. 最后同步 `SKILL.md`

## 什么时候应该拆成多个工具

如果你发现一个 `llm-tool.yaml` 里的参数越来越多，而且这个工具开始负责多种完全不同的行为，通常说明它应该拆分了。

更好的模式通常是：

- 一个工具做一类明确动作
- 多个动作拆成多个工具

这样更容易维护，也更容易让宿主正确调用。
